## Locators are descriptions

A locator says how to find an element: "the button named Add to cart", "the row that mentions Ada". It isn't the
element. Making one does nothing and can't fail, and every time it's used, it looks at the page as it is then. A
locator made before the page re-renders still finds the new element after.

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const signIn = Effect.fn("signIn")(function*(page: Page.Page) {
  const email = page.getByLabel("Email")
  const submit = page.getByRole("button", { name: "Sign in" })
  yield* email.fill("ada@example.com")
  yield* submit.click()
})
```

Every query runs in Strider's own query engine, which it adds to each document, so a query means the same thing in
Chromium, Firefox and WebKit.

## The queries

Find elements the way a person using the page would: by what they are and what they say.

| Query                                | Finds                                                         |
| ------------------------------------ | ------------------------------------------------------------- |
| `getByRole(role, { name })`          | elements with an ARIA role and, optionally, an accessible name |
| `getByText(text)`                    | the smallest elements whose text matches                       |
| `getByLabel(text)`                   | form controls whose label matches                              |
| `getByPlaceholder(text)`             | inputs whose placeholder matches                               |
| `getByAltText(text)`                 | images and areas whose alt text matches                        |
| `getByTitle(text)`                   | elements whose `title` matches                                 |
| `getByTestId(id)`                    | elements whose `data-testid` is `id`                           |
| `locator(css)`                       | elements matching a CSS selector                               |

Prefer `getByRole`. A role and a name are what assistive technology sees, so a locator written that way checks
that the page is usable, and it survives a redesign that changes classes and markup. Roles and names are computed
by the standards browsers use for assistive technology, HTML-AAM and accname 1.2. Elements hidden from the
accessibility tree aren't matched unless you pass `includeHidden: true`.

A string matches as a case-insensitive substring. Pass `exact: true` to match the whole text, case-sensitively, or
a `RegExp` to test it your own way:

```ts
import { Page } from "@usestrider/browser"

declare const page: Page.Page

page.getByRole("button", { name: "Save" }) // "Save" and "Save draft"
page.getByRole("button", { name: "Save", exact: true }) // only "Save"
page.getByText(/^\d+ items?$/) // "1 item", "12 items"
```

Text is an element's text content with whitespace collapsed, through open shadow roots, without scripts and
styles. It isn't `innerText`, which depends on layout and differs between browsers. `getByText` finds the smallest
element that says it, so `<p>1 <b>item</b></p>` is found by `"1 item"`, as the paragraph.

A CSS selector that doesn't parse fails with `InvalidInput` as soon as it's used, without waiting.

## Narrowing

Queries chain: each one searches inside the matches of the one before.

```ts
import { Page } from "@usestrider/browser"

declare const page: Page.Page

const nav = page.getByRole("navigation", { name: "Main" })
const orders = nav.getByRole("link", { name: "Orders" })
```

`filter` keeps the matches that satisfy a condition. `hasText` and `hasNotText` test an element's text;
`visible` keeps only visible or only hidden matches; `has` and `hasNot` test what an element contains:

```ts
import { Locator, Page } from "@usestrider/browser"

declare const page: Page.Page

const adasRow = page.getByRole("row").filter({ hasText: "Ada Lovelace" })

const deletable = page.getByRole("row").filter({
  has: Locator.relative.getByRole("button", { name: "Delete" })
})
```

`has` takes a relative locator, built from `Locator.relative`, which starts from the element being tested rather
than from the page. Passing a locator that starts from the page is a type error, so a filter can't silently search
the whole document.

`and` keeps elements both locators match, `or` elements either matches. `first`, `last` and `nth(index)` pick by
position:

```ts
import { Page } from "@usestrider/browser"

declare const page: Page.Page

const primary = page.getByRole("button").and(page.locator(".primary"))
const ok = page.getByRole("button", { name: "OK" })
const confirm = ok.or(page.getByRole("button", { name: "Continue" }))
const newest = page.getByRole("listitem").first
```

Use position as a last resort: a positional locator breaks as soon as the order changes. Errors say when a locator
picked by position.

## Labels

`describe` gives a locator a label for errors and traces, in place of the code that built it:

```ts
import { Page } from "@usestrider/browser"

declare const page: Page.Page

const badge = page.locator("header .cart > span").describe("cart badge")
```

## Frames

An iframe's document is entered through its element. `page.frame` takes a locator for the iframe and gives a frame
locator, which has the same queries:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const payByCard = Effect.fn("payByCard")(function*(page: Page.Page) {
  const payment = page.frame(page.locator("iframe#payment"))
  yield* payment.getByLabel("Card number").fill("4242 4242 4242 4242")
  yield* payment.getByRole("button", { name: "Pay" }).click()
})
```

Like any locator, a frame locator finds its iframe again on every attempt, so a frame that reloads or arrives late
is treated like an element that isn't there yet. Cross-site frames work the same way, and frames
nest: `payment.frame(payment.locator("iframe"))`.

## Strictness

An action or a read needs exactly one match. A locator that matches several fails at once with `StrictViolation`,
listing what it found. One that matches nothing is waited for by an action or an expectation, and fails a read at
once with `NoMatch`. [Errors and deadlines](/docs/errors#strict-by-default) says why ambiguity doesn't wait.

`count` and `all` are the reads that take any number of matches. `all` gives a locator for each current match,
pinned to its position:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const productNames = Effect.fn("productNames")(function*(page: Page.Page) {
  const cards = yield* page.getByRole("article").all
  return yield* Effect.forEach(cards, (card) => card.getByRole("heading").readText)
})
```

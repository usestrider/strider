A locator finds an element for an action, read, or expectation, usually by what a person sees: a button's role and
name, a field's label, or text.

## Locators and elements

A locator is how to find an element, not the element. Making one does nothing and can't fail; each use looks at
the page as it is then.

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const signIn = Effect.fn("signIn")(function*(page: Page.Page) {
  const email = page.getByLabel("Email")
  const submit = page.getByRole("button", { name: "Sign in" })
  yield* email.fill("ada@example.com")
  yield* submit.click()
})
```

Queries, the `getBy…` methods and `locator`, run in Strider's own engine in each document, apart from the page's
scripts, so they mean the same on every browser. On WebKit, which has no
[isolated worlds](/docs/browsers/webkit#isolated-worlds), the engine runs beside the page's scripts, and a page
that replaces the built-ins it uses can change what queries find.

## The queries

| Query                                | Finds                                                         |
| ------------------------------------ | ------------------------------------------------------------- |
| `getByRole(role, { name })`          | elements with an ARIA role and, optionally, an accessible name |
| `getByText(text)`                    | the smallest elements whose text matches                       |
| `getByLabel(text)`                   | form controls whose label matches                              |
| `getByPlaceholder(text)`             | inputs whose placeholder matches                               |
| `getByAltText(text)`                 | images and areas whose alt text matches                        |
| `getByTitle(text)`                   | elements whose `title` matches                                 |
| `getByTestId(id)`                    | elements whose `data-testid` is `id`                           |
| `locator(css)`                       | elements matching a CSS selector                               |

Prefer `getByRole`: roles and names are what assistive technology sees, and they survive changes to markup and
classes. An accessible name is what a screen reader announces for an element: a button's text, a field's label, or
its `aria-label`. They're computed by [HTML-AAM](https://www.w3.org/TR/html-aam-1.0/) and
[accname 1.2](https://www.w3.org/TR/accname-1.2/).

A malformed CSS selector fails with [`InvalidInput`](/docs/errors#three-kinds-of-failure) when used, without
waiting.

## Matching text

A string matches as a case-insensitive substring, so `name: "Save"` also finds "Save draft". `exact: true` matches
the whole text, case-sensitively, and a `RegExp` is tested as given. A role's hidden elements match only with
`includeHidden: true`:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const saveCart = Effect.fn("saveCart")(function*(page: Page.Page) {
  const saves = page.getByRole("button", { name: "Save" }) // "Save" and "Save draft"
  yield* saves.pipe(Expect.toHaveCount(2))
  const email = page.getByLabel("Email", { exact: true }) // not "Email confirmation"
  yield* email.fill("ada@example.com")
  const save = page.getByRole("button", { name: "Save", exact: true }) // only "Save"
  yield* save.click()
  const items = page.getByText(/^\d+ items?$/) // "1 item", "12 items"
  yield* items.pipe(Expect.toBeVisible)
  const cookies = page.getByRole("dialog", {
    name: "Cookie settings",
    includeHidden: true // even while hidden
  })
  yield* cookies.pipe(Expect.toBeHidden)
})
```

Text is text content with whitespace collapsed, through open shadow roots, not `innerText`. `getByText` finds the
smallest element that has it: `"1 item"` finds the `<p>` in `<p>1 <b>item</b></p>`.

## Role states

When several elements share a role and name, state filters select the one in the state you need. Combine filters
with a name; omitted filters accept every state.

```ts
import { Page } from "@usestrider/browser"

declare const page: Page.Page

const heading = page.getByRole("heading", { level: 2 })
const checked = page.getByRole("checkbox", { checked: true })
const toggle = page.getByRole("button", { name: "Mute", pressed: true })
const collapsed = page.getByRole("button", { expanded: false })
const selected = page.getByRole("tab", { selected: true })
const enabled = page.getByRole("button", { name: "Save", disabled: false })
```

Native controls use their native states; ARIA controls use the corresponding ARIA attributes. Disabled state is
inherited, including disabled fieldsets. Options inherit native disabled state from optgroups and fieldsets,
but not selects. For options and optgroups, these filters can differ from enabled reads and action checks,
which retain the browser's native behavior. Mixed checked or pressed states match neither boolean. Missing expanded
state also matches neither boolean; present expanded values other than case-insensitive `"true"` match false.
Missing pressed or selected state matches false. Unsupported role/filter combinations fail when used, even
with an empty scope or a missing frame: locator operations return `LocatorError` with an `InvalidInput` reason, and expectations
return `ExpectationFailed`. See
[`RoleOptions`](/docs/api/browser/Locator#roleoptions) for the supported roles and state-reading details.

## Narrowing

Narrowing searches one region, or keeps only the matches you mean, such as the header's link when the footer has
the same one. Each query in a chain searches inside the previous one's matches:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const openOrders = Effect.fn("openOrders")(function*(page: Page.Page) {
  const nav = page.getByRole("navigation", { name: "Main" })
  const orders = nav.getByRole("link", { name: "Orders" })
  yield* orders.click()
})
```

`filter` keeps matches by `hasText`, `hasNotText`, `visible`, or what they contain, `has` and `hasNot`.

Use `has` and `hasNot` to test for an element rather than for text. They take a `Locator.relative` locator, which
starts at the element being tested; a page locator there is a type error. A filter keeps the matches that meet all
it's given:

```ts
import { Locator, Page } from "@usestrider/browser"
import { Effect } from "effect"

const cancelOrder = Effect.fn("cancelOrder")(
  function*(page: Page.Page, customer: string) {
    const order = page.getByRole("row").filter({
      hasText: customer,
      hasNotText: "Shipped",
      has: Locator.relative.getByRole("button", { name: "Cancel order" }),
      hasNot: Locator.relative.getByRole("img", { name: "On hold" }),
      visible: true
    })
    yield* order.getByRole("button", { name: "Cancel order" }).click()
  }
)
```

`or` matches either locator, for a control whose label changes with its state; `and` keeps the elements both
match. `first`, `last`, and `nth(index)` pick by position, for a list whose order means something.
`nth(index)` counts from 0; negative indexes and indexes past the end match nothing. `first` and `last` also
match nothing on an empty list. Errors and traces keep the selection you wrote:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const confirm = Effect.fn("confirm")(function*(page: Page.Page) {
  const ok = page.getByRole("button", { name: "OK" })
  yield* ok.or(page.getByRole("button", { name: "Continue" })).click()
})

const saveToAccount = Effect.fn("saveToAccount")(function*(page: Page.Page) {
  const save = page.getByRole("button", { name: "Save" })
  yield* save.and(page.getByTitle("Save to your account")).click()
})

// The inbox lists the newest message first
const inbox = (page: Page.Page) =>
  page.getByRole("list", { name: "Inbox" }).getByRole("listitem")

const archiveOldest = Effect.fn("archiveOldest")(function*(page: Page.Page) {
  yield* inbox(page).last.getByRole("button", { name: "Archive" }).click()
})

const openMessage = Effect.fn("openMessage")(function*(page: Page.Page, index: number) {
  yield* inbox(page).nth(index).click() // counting from 0: nth(0) is first, the newest
})
```

Pick by position last: it breaks when the order changes.

## Labels

`describe` gives a locator a label, which errors and [traces](/docs/tools/recordings#traces) show in place of its
queries, so a failure names the cart badge rather than `header .cart > span`:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const cartCount = Effect.fn("cartCount")(function*(page: Page.Page) {
  const badge = page.locator("header .cart > span").describe("cart badge")
  return yield* badge.readText
})
```

With no badge on the page, `cartCount` fails with:

```
Locator.readText cart badge: Nothing matched (A read never waits; Expect waits for what it expects)
```

A label names that locator only: one built from it, such as `badge.first` or `badge.filter({ visible: true })`, is
named by its queries again, so call `describe` last.

## Frames

A query searches one document, and an iframe, such as an embedded payment form, holds its own. `page.frame` takes a
locator for an iframe and gives a frame locator, which has the same queries and searches inside it:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const payByCard = Effect.fn("payByCard")(function*(page: Page.Page) {
  const payment = page.frame(page.locator("iframe#payment"))
  yield* payment.getByLabel("Card number").fill("4242 4242 4242 4242")
  yield* payment.getByRole("button", { name: "Pay" }).click()
})
```

It finds the iframe again on every attempt, so a frame that reloads or arrives late is waited for like any
element. Cross-site frames work the same, and frames nest: `payment.frame(payment.locator("iframe"))`.

## Counting matches

An action or read needs exactly one match: several fail it at once with
[`StrictViolation`](/docs/errors#strictness), and none is waited for by an action or expectation, and fails a
read at once with [`NoMatch`](/docs/api/browser/Locator#NoMatch). For a list of any length, `count` and `all` take
any number, and read once without waiting, so expect the list first. `all` gives a locator per current match:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const productNames = Effect.fn("productNames")(function*(page: Page.Page) {
  const cards = page.getByRole("article")
  yield* cards.first.pipe(Expect.toBeVisible)
  yield* Effect.log(`${yield* cards.count} products`)
  const each = yield* cards.all
  return yield* Effect.forEach(each, (card) => card.getByRole("heading").readText)
})
```

## Reading a position

An element can be offscreen or transparent and still have a layout box. `boundingBox` reads that box without
scrolling or moving focus, including when the page is readonly:

```ts
import { Page } from "@usestrider/browser"
import { Effect, Option } from "effect"

const savePosition = Effect.fn("savePosition")(function*(page: Page.ReadonlyPage) {
  const box = yield* page.getByRole("button", { name: "Save" }).boundingBox
  if (Option.isSome(box)) yield* Effect.log(box.value.x, box.value.y)
})
```

Coordinates are CSS pixels relative to the main frame's viewport, including child-frame borders and padding.
Scrolling can make them negative. `None` means the matched element has no layout box, such as `display: none`;
hidden, transparent, and zero-size elements retain their boxes. A missing element fails with `NoMatch`, and
several matches fail with `StrictViolation`. The target's box follows the browser's own
`getBoundingClientRect`, including its transforms, motion paths, and camera clipping. It is composed through
frames rather than reconstructing original corners or measuring painted pixels.

Chromium and WebKit use native frame point conversion. Firefox supports positive axis-aligned scaling, CSS
zoom, and translation of frames. Rotation, skew, reflection, 3D, perspective, or motion paths on a frame or its
ancestors fail with descriptive typed `Unsupported` on Firefox. These frame limits do not prevent reading a
top-level target's own browser rect. Browser defaults stay unchanged; no launch profile or preference is required.

Input sent to an element that's hidden, moving or covered misses it or lands on something else, and a sleep before
each step only makes that less likely. An action waits until its element can take the input, then sends it once.

## The actions

An action is a locator method, with settings as an optional last argument:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const editProfile = Effect.fn("editProfile")(function*(page: Page.Page) {
  yield* page.getByLabel("Name").fill("Ada Lovelace")
  yield* page.getByLabel("Country").selectOption({ label: "United Kingdom" })
  yield* page.getByLabel("Send me the newsletter").check()
  yield* page.getByRole("button", { name: "Save" }).click()
})

const openRowMenu = Effect.fn("openRowMenu")(function*(page: Page.Page, name: string) {
  const row = page.getByRole("row").filter({ hasText: name })
  yield* row.click({ button: "right" })
})
```

| Action                        | Does                                                                      |
| ----------------------------- | ------------------------------------------------------------------------- |
| `click()`, [`dblclick()`](/docs/api/browser/Locator#Locator.dblclick) | moves the pointer to the element, presses and releases                     |
| [`tap()`](/docs/api/browser/Locator#Locator.tap) | a touch start and end; on WebKit, which has no touch, fails with `Unsupported` |
| [`hover()`](/docs/api/browser/Locator#Locator.hover) | moves the pointer over the element                                         |
| `check()`, [`uncheck()`](/docs/api/browser/Locator#Locator.uncheck) | clicks a checkable unless it's already in that state, then confirms the change |
| `fill(value)`                 | focuses a field, selects its contents and inserts the value; `""` empties it |
| `clear()`                     | empties a field                                                            |
| `press(key)`                  | focuses the element and presses a key                                      |
| `pressSequentially(text)`     | focuses the element and types the text key by key                         |
| `selectOption(choice)`        | chooses a `<select>`'s option by `value`, `label` or `index`                |
| `setInputFiles(files)`        | sets a file input's files                                                  |
| `dragTo(target)`              | presses on the element, moves to the target with the button held, releases |
| [`focus()`](/docs/api/browser/Locator#Locator.focus), [`scrollIntoView()`](/docs/api/browser/Locator#Locator.scrollIntoView) | focuses it, or scrolls it into view                                        |

In a design-mode document, filling a paragraph blurs a previously focused input or textarea, including one
inside open shadow roots, and checks the target again after its blur handlers. If refocusing prevents preparation
until the deadline, the timeout's history reports the focus preparation. Firefox cannot focus inputs in top-level design-mode documents:
filling one can insert text into the document body instead. This is a known browser limitation of
[`fill`](/docs/api/browser/Locator#Locator.fill).

An action sends its input at most once. If it fails after the input may have reached the page, the error's
[`diagnostics.dispatch`](/docs/errors#diagnostics) says so.

Unchecking a checked native radio fails with `WrongElement` before input, including with
`uncheck({ trial: true })`. Check another radio in the group instead. An already-unchecked native
radio is a no-op; page-managed ARIA radios can be unchecked.

A text descendant of a label can check or uncheck its associated checkbox. For
`<input id="terms" type="checkbox"><label for="terms"><span>Accept terms</span></label>`:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const acceptTerms = Effect.fn("acceptTerms")(function*(page: Page.Page) {
  yield* page.getByText("Accept terms").check()
  yield* page.getByText("Accept terms").uncheck()
})
```

If a label covers its control, targeting the control times out because the label receives the pointer.
Target the label's text instead, as `getByText("Accept terms").check()` above does; Strider clicks that
text and checks the associated control's state.

The click stays on the text you selected, and a box already in the right state gets no input. If the text
sits inside something interactive of its own, such as a link or a button, the action fails with
`WrongElement` before sending anything. Inside a closed shadow root Strider can't see that control, so the
click can land on it, and the action then fails with `StateUnchanged`. The full rules are in
[`check`](/docs/api/browser/Locator#Locator.check)'s reference.

## Checks

Before sending anything, an action checks whether its element is ready and retries at each animation frame when it is not:

| Action                                                            | Checks                                                                   |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `click`, `dblclick`, `tap`, `check`, `uncheck`, `dragTo`, `hover` | visible, stable, enabled, not inert, in the viewport, receives the pointer |
| `fill`, `clear`                                                   | visible, enabled, editable, not inert                                    |
| `focus`, `press`, `pressSequentially`                             | visible, not inert                                                       |
| `scrollIntoView`                                                  | visible, stable                                                          |
| `selectOption`                                                    | visible, enabled                                                         |
| `setInputFiles`                                                   | none                                                                     |

Pointer actions (`click`, `dblclick`, `tap`, `check`, `uncheck`, `dragTo` and `hover`) default to
`checks.rendered: true`: they wait for a drawn frame because pointer routing uses what the browser last drew.
A drag waits at both endpoints. All other actions, including `clear`, default to `checks.rendered: false` and
check current layout immediately. Stability still waits for its requested frames, independently of this setting.
Every action checks again after acquiring the page's input permit, with the same rendering choice.

A server-rendered input can accept a fill before the framework hydrates it, then lose that value during hydration.
Wait for an app-defined readiness condition, or enable the frame wait for one call; Playwright has the same race.
A drawn frame alone does not guarantee hydration has finished:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const enterName = Effect.fn("enterName")(function*(page: Page.Page) {
  yield* page.getByLabel("Name").fill("Ada", { checks: { rendered: true } })
})
```

With `rendered: false`, an action can succeed even when the page is not drawing. If another check keeps it
waiting, its timeout reports that readiness reason without the “page rendered no frame” hint. You can also
set `rendered: false` on a pointer action when your application can tolerate routing against the last drawn frame.

An action needs its element reachable; visible means a person can see it. Actions accept an element with `opacity: 0` on itself or any ancestor. For that element, `isVisible` returns false, `Expect.toBeVisible` waits, and `filter({ visible: true })` excludes that element; `filter({ visible: false })` includes it. Opacity alone does not make an action wait for a fade-in.

An action's `visible` check requires CSS visibility, content visibility and a nonempty box. Pointer actions require their action point to receive the pointer, so a covering element blocks them. Non-pointer actions accept transparency without a pointer hit test: `fill` and `clear` require enabled, editable and not inert; `focus`, `press` and `pressSequentially` require not inert; `selectOption` requires enabled; `scrollIntoView` requires stability. `setInputFiles` runs no readiness checks.

- "Stable": stopped moving. "In the viewport": scrolled there. "Receives the pointer": nothing covers the point.
  "Not inert": not under an `inert` attribute, nor outside an open modal dialog.
- After the checks pass, it checks once more and sends. If something covers a click's target in between, the page
  never sees the click, and the action checks again.
- A timeout's hint names the last failed check:
  `Another element covers the element's action point: div.toast "Saved"`.

## Turning checks off

An element that never passes a check, such as a button that pulses forever, times out. Turn single checks off with
`checks`, by key: `visible`, `stable`, `enabled`, `editable`, `notInert`, `inViewport` and `receivesPointer`.
There's no blanket `force`: turning off one check rather than all keeps the rest guarding the action. `trial: true`
does the reverse, running the checks and sending nothing, to learn whether an action would go through without
causing it:

```ts
import { Deadline, Page } from "@usestrider/browser"
import { Effect } from "effect"

const claimOffer = Effect.fn("claimOffer")(function*(page: Page.Page) {
  const pulsing = page.getByRole("button", { name: "Claim offer" })
  yield* pulsing.click({ checks: { stable: false } })
})

const canDelete = Effect.fn("canDelete")(function*(page: Page.Page) {
  const remove = page.getByRole("button", { name: "Delete" })
  return yield* remove.click({ trial: true }).pipe(
    Deadline.within("2 seconds"),
    Effect.as(true),
    Effect.catchTag("Timeout", () => Effect.succeed(false))
  )
})
```

A trial that passes succeeds; one whose checks never pass times out, like the action would.

## Typing

- `fill` inserts text as pasting would: the page sees input events, not key presses. A date, color or range input
  has its value set, and a value it refuses fails with [`InvalidInput`](/docs/errors#three-kinds-of-failure).
- `pressSequentially` sends a key per character, for fields that react to each keystroke. `delay` spaces them, for
  a field that drops keys typed faster than it handles them.
- Pass secrets as `Redacted`. The value is typed, and never appears in errors, spans, logs or traces:

```ts
import { Page } from "@usestrider/browser"
import { Config, Effect } from "effect"

const logIn = Effect.fn("logIn")(function*(page: Page.Page) {
  yield* page.getByLabel("Email").fill("ada@example.com")
  yield* page.getByLabel("Password").fill(yield* Config.Redacted("APP_PASSWORD"))
  yield* page.getByRole("button", { name: "Sign in" }).click()
})
```

For an autocomplete:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const chooseCity = Effect.fn("chooseCity")(function*(page: Page.Page) {
  const city = page.getByRole("combobox", { name: "City" })
  yield* city.clear()
  yield* city.pressSequentially("Lisb", { delay: "50 millis" })
  yield* page.getByRole("option", { name: "Lisbon, Portugal" }).click()
})
```

## Keys

Keys use UI Events names, as in `event.key`: `"Enter"`, `"Tab"`, `"ArrowDown"`, `"a"`. Modifiers are an option;
there's no `"Control+A"`:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const copyAll = Effect.fn("copyAll")(function*(page: Page.Page) {
  const editor = page.getByRole("textbox", { name: "Notes" })
  yield* editor.press("a", { modifiers: ["Control"] })
  yield* editor.press("c", { modifiers: ["Control"] })
})
```

Typing uses a US layout unless the context sets another. A character the layout has no key for, such as `ß`, is
typed as a key of its own with an empty `code`, which a page that reads `code` won't expect. Set the layout the
page's users have, and Shift, AltGr and dead keys type as they would:

```ts
import { Browser } from "@usestrider/browser"
import { Effect } from "effect"

const germanAddress = Effect.fn("germanAddress")(function*() {
  const page = yield* Browser.newPage({ keyboardLayout: "de" })
  yield* page.goto("https://shop.example.de/checkout")
  yield* page.getByLabel("Straße").pressSequentially("Hauptstraße 5")
}, Effect.scoped)
```

Layouts: `us`, `uk`, `de`, `fr`, `es`, `it`. On Firefox a layout still types, each key with the `code` it has on a
US keyboard and with no AltGr or dead keys. WebKit types characters and named keys, and fails with `Unsupported` at
a character the layout reaches with AltGr or a dead key, before that key is sent; `pressSequentially` has already
typed the characters before it.

## Files

`setInputFiles` chooses files without opening the operating system’s picker. `FileInput.local` names a file on
this machine; `FileInput.bytes` supplies generated contents:

```ts
import { FileInput, Page } from "@usestrider/browser"
import { Effect } from "effect"

const changeAvatar = Effect.fn("changeAvatar")(function*(page: Page.Page) {
  yield* page.getByLabel("Avatar").setInputFiles(FileInput.local("./avatar.png"))
})

const importReport = Effect.fn("importReport")(function*(page: Page.Page, csv: string) {
  const report = FileInput.bytes(
    "report.csv",
    "text/csv",
    new TextEncoder().encode(csv)
  )
  yield* page.getByLabel("Report").setInputFiles(report)
})
```

A launched browser receives local paths directly. Absolute paths need no caller services; relative paths need the
path [platform service](/docs/installation#platform-services). A launch through a container or wrapper with a
different file system needs `FileInput.bytes` instead.

Attached connections copy local contents using captured file-system and path
[platform services](/docs/installation#platform-services), including for absolute paths. Local files can combine
with bytes on attached connections, or with [remote paths](/docs/api/browser/FileInput#remote) on launched ones.
A selection cannot combine native paths and transferred contents; it fails before replacing the previous files.

An upload through a file chooser, not an input, is answered with
[`FileChooser.handle`](/docs/events/kinds#dialogs-and-file-choosers).

## Dragging

`dragTo` drags with the pointer. A native HTML drag (`draggable="true"`) works only on Chromium, and fails
elsewhere with `Unsupported` before anything is sent; `html: "synthetic"` has the page dispatch the drag's events
instead, on every browser. They're untrusted: their `isTrusted` is `false`, so a page that checks it can tell them
from a user's:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const moveToDone = Effect.fn("moveToDone")(function*(page: Page.Page, title: string) {
  const card = page.getByRole("listitem").filter({ hasText: title })
  const done = page.getByRole("list", { name: "Done" })
  yield* card.dragTo(done, { html: "synthetic" })
})
```

## The keyboard and the mouse

`page.keyboard` types into whatever has focus, for a shortcut the page itself handles. Its `insertText` adds text
at the caret with no key events, as an input method would, where `fill` replaces the field's contents; on Firefox,
which has no command for it, each character is typed as a key.
`page.mouse` acts at coordinates, for canvases and maps. Neither checks anything. Holding a key or button is
scoped, so a failed step never leaves it held:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const openShortcuts = Effect.fn("openShortcuts")(function*(page: Page.Page) {
  yield* page.keyboard.press("?")
  yield* page.getByRole("dialog", { name: "Keyboard shortcuts" }).pipe(
    Expect.toBeVisible
  )
})

const searchNearTokyo = Effect.fn("searchNearTokyo")(function*(page: Page.Page) {
  yield* page.getByRole("searchbox").fill("Hotels near ")
  yield* page.keyboard.insertText("東京")
})

const selectRange = Effect.fn("selectRange")(function*(page: Page.Page) {
  yield* page.getByRole("option", { name: "Apples" }).click()
  yield* Effect.scoped(Effect.gen(function*() {
    yield* page.keyboard.hold("Shift")
    yield* page.getByRole("option", { name: "Pears" }).click()
  }))
})

const sketch = Effect.fn("sketch")(function*(page: Page.Page) {
  yield* page.mouse.move({ x: 100, y: 100 })
  yield* Effect.scoped(Effect.gen(function*() {
    yield* page.mouse.hold("left")
    yield* page.mouse.move({ x: 220, y: 140 }, { steps: 12 })
  }))
})

const zoomMap = Effect.fn("zoomMap")(function*(page: Page.Page) {
  yield* page.mouse.move({ x: 400, y: 300 })
  yield* page.mouse.wheel({ x: 0, y: -240 })
})
```

A click while Shift is held is a Shift-click; moves while a button is held are a drag. Input to one page goes one
gesture at a time, so two fibers acting on one page never interleave their presses: the second
[waits its turn](/docs/deadlines#setting-a-deadline), within its deadline.

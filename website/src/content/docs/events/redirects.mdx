---
title: Redirect chains
description: Following a request through its redirects.
order: 4
---

`NetworkRequest.redirects` gives a handle that reads the request before or after another in its chain. It follows
the requests themselves, not their URLs, since a chain can visit one URL twice, and says when it can't tell whether
a request was the last, rather than calling it the end.

```ts
import { NetworkRequest, Page } from "@usestrider/browser"
import { Effect, Option } from "effect"

const successorSeen = Effect.fn("successorSeen")(function*(page: Page.Page) {
  const redirects = yield* NetworkRequest.redirects(page)
  const sent = yield* NetworkRequest.next(page, { url: "https://example.com/start" })
  yield* page.goto("https://example.com/start")
  const first = yield* sent
  const next = yield* redirects.to(first).pipe(
    Effect.catchReason("RequestError", "RedirectUnknown", () => Effect.succeedNone)
  )
  return Option.map(next, (request) => request.url)
})
```

This one-step recovery handles only `RedirectUnknown`. Its `None` means no successor was seen; it does not prove
that the chain ended. Eviction, foreign ownership, copied snapshots, release, and target closure remain errors.
Omit the recovery when the difference between a proven boundary and uncertainty matters.

The handle's `from(request)` and `to(request)` read immediately and never wait. Pass the original snapshot from
that page's or context's [request events](/docs/events/network). A copied or decoded snapshot cannot establish
ownership. `from` returns `None` for the first hop. `to` returns observed successors first, including canceled
attempts. Otherwise `None` requires a completed failure, a completed non-redirect response, or a retained committed
navigation outcome naming this exact response hop. That last proof covers a navigation to a 302 without Location.

The browser protocols have different limits:

- Chromium can report a canceled successor attempt for a manual fetch. The lookup preserves that observed link,
  as Playwright does on the same pinned Chromium.
- Firefox reports redirect completion before reporting its successor and exposes no fetch redirect mode.
  Its completed manual fetch can remain unknown.
- WebKit's manual fetch can have no reported successor. Without retained terminal navigation proof it also
  remains unknown.

A lookup fails with `RequestError`, whose reason is one of:

- `RedirectUnknown`: `inFlight` before the hop ends, or `completedRedirect` after a redirect response when neither
  a successor nor terminal navigation proof is retained. Completion, status, and Location alone cannot prove an end.
- `RedirectUnavailable`: `evicted` for a request or neighbor outside retention, `foreignTarget` for a retained hop
  owned by another page or context, `unavailable` for a copied snapshot, missing response evidence, or an absent navigation outcome in disabled or
  incomplete history, `released`
  when the acquiring scope ends, or `targetClosed` when the target or connection closes.

Access reuses the existing connection-wide index of at most 1000 hops. Completed hops are evicted oldest first,
then unfinished hops if necessary; another context can evict evidence too. Navigation proof reuses the page's
bounded [event history](/docs/events/events#next-stream-and-history); an absent navigation outcome
cannot establish a boundary. If its history is disabled or has dropped entries, the lookup reports unavailable
evidence; the one-step unknown recovery preserves this error. The handle can inspect retained requests from before it opened. It adds no request
cache, event listener, or protocol command, and closing its scope revokes further lookups.

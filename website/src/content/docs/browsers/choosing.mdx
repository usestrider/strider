Each browser's protocol lets Strider do a different set of things, so a step that passes on Chromium can fail with
`Unsupported` on Firefox or WebKit. Knowing what each backend can do lets you pick the one a program needs, and run
one program on all three, skipping only what a browser lacks.

## Three backends

| Backend  | Engine | Protocol                              | Launches                       | Attaches to                                  |
| -------- | ------ | ------------------------------------- | ------------------------------ | -------------------------------------------- |
| Chromium | Blink  | Chrome DevTools Protocol              | Chromium, Chrome, Edge         | a browser started with a debugging port      |
| Firefox  | Gecko  | WebDriver BiDi                        | Firefox                        | Firefox's remote agent, or any BiDi endpoint |
| WebKit   | WebKit | WebKit's Automation and inspector protocols | WebKitGTK's or WPE's MiniBrowser | a WebKitGTK or WPE browser's inspector server |

The rest of the guide works on all three, except where a browser lacks a capability. That fails with
`Unsupported`, naming it, before anything is sent.

- **[Chromium](/docs/browsers/chromium)** supports the most: start here, and use it for throttling, media emulation
  or PDFs.
- **[Firefox](/docs/browsers/firefox)** runs over WebDriver BiDi, the W3C standard, which covers less emulation and
  interception than CDP.
- **[WebKit](/docs/browsers/webkit)** is stock WebKitGTK and WPE, Linux only. It supports the least: no
  [`Popup.next`](/docs/events/kinds#popups), since WebKit names no opener; no downloads or file choosers; and no
  [`back`](/docs/api/browser/Page#Page.back) or [`forward`](/docs/api/browser/Page#Page.forward).

## Capabilities

Generated from each backend's capability list, the one `browser.capabilities` returns. Hover a cell for the reason
it's missing or partial. Columns are launched browsers; a second line says when attaching differs. A dash means the
backend doesn't list that capability: WebKit alone lists some things the others simply have, and Firefox alone
lists WebDriver input.

## Running on every browser

A program needs a `Browser`, which a layer provides, so the same program or tests run on every backend by changing
the layer. Each backend requires its own [platform services](/docs/installation#platform-services), WebKit's
including a [`SocketConnector`](/docs/browsers/webkit#launching); provide them all, and the layers are
interchangeable:

```ts
import { NodeServices, NodeSocket } from "@effect/platform-node"
import { layer } from "@effect/vitest"
import { Browser, Expect } from "@usestrider/browser"
import { Chromium } from "@usestrider/browser/chromium"
import { Firefox } from "@usestrider/browser/firefox"
import { SocketConnector } from "@usestrider/browser/protocol"
import { WebKit } from "@usestrider/browser/webkit"
import { VitestBrowser } from "@usestrider/vitest"
import { Config, Effect, Layer } from "effect"

const Sockets = SocketConnector.layer((endpoint) =>
  NodeSocket.makeNet({ host: endpoint.host, port: endpoint.port })
)

const Platform = Layer.mergeAll(
  NodeServices.layer,
  NodeSocket.layerWebSocketConstructor,
  Sockets
)

const path = (name: string) => ({ executablePath: Config.String(name) })

const backends = {
  chromium: Chromium.layerConfig(path("CHROMIUM_PATH")).pipe(Layer.provide(Platform)),
  firefox: Firefox.layerConfig(path("FIREFOX_PATH")).pipe(Layer.provide(Platform)),
  webkit: WebKit.layerConfig(path("WEBKIT_PATH")).pipe(Layer.provide(Platform))
}

for (const [name, backend] of Object.entries(backends)) {
  layer(VitestBrowser.layer(backend), { excludeTestServices: true })(name, (it) => {
    it.effect("adds a product to the cart", () =>
      Effect.gen(function*() {
        const page = yield* Browser.newPage()
        yield* page.goto("https://shop.example.com")
        yield* page.getByRole("button", { name: "Add to cart" }).click()
        yield* page.getByText("1 item").pipe(Expect.toBeVisible)
      }))
  })
}
```

Each `layer` block launches its own browser. Blocks in one file run in turn; put each backend in its own file to
run them in parallel.

## Checking capabilities

A step a backend can't do fails with `Unsupported`, so a program meant for every backend has to know where to do
without it. Check the capability first when the answer changes what the program does; recover from `Unsupported`
when the step can be skipped. [`browser.capabilities`](/docs/api/browser/Browser#Browser.capabilities) is the
connected browser's list, and `has` says whether an entry is fully supported. It takes a capability's name, the one
an [`Unsupported` reason's `capability`](/docs/errors#recovering) gives, such as `"emulation.media"`:

```ts
import { Browser, Page } from "@usestrider/browser"
import { Effect } from "effect"

// Where the browser can't emulate the setting, use the site's own switch
const darkMode = Effect.fn("darkMode")(function*(page: Page.Page) {
  const browser = yield* Browser.Browser
  const capabilities = yield* browser.capabilities
  if (capabilities.has("emulation.media")) {
    yield* page.emulate({ media: { colorScheme: "dark" } })
  } else {
    yield* page.getByRole("button", { name: "Dark theme" }).click()
  }
})
```

Or try it and recover from `Unsupported`, which any module's error can carry: here `DeclarationError`, the error
of a [declaration](/docs/events/routes#declarations) such as `emulate`:

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

// A screenshot is steadier without animations, but can be taken without
const steadyScreenshot = Effect.fn("steadyScreenshot")(function*(page: Page.Page) {
  return yield* Effect.scoped(Effect.gen(function*() {
    yield* page.emulate({ media: { reducedMotion: "reduce" } }).pipe(
      Effect.catchReason("DeclarationError", "Unsupported", () => Effect.void)
    )
    return yield* page.screenshot()
  }))
})
```


## Platform coverage

Linux integration tests cover Chromium 155.0.8059.79, Firefox 158.0 and WebKitGTK 2.54.1 in a pinned Nix
environment. The macOS entry point covers the Chromium and Firefox adapter and public API slice suites with
Chrome for Testing 155.0.8059.79 and Firefox 158.0 on Apple Silicon; its first CI run is pending. Browser
versions are checked exactly on both platforms. macOS uses the runner's fonts and native display, so its
rendering can differ from Linux. Safari, Intel macOS and Windows are not covered by this macOS entry point.

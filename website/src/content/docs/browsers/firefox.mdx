## Firefox and WebDriver BiDi

Strider drives Firefox over WebDriver BiDi, the W3C's standard protocol for automating browsers, which Firefox's
remote agent speaks. Since CDP was removed from Firefox, BiDi is the only protocol Firefox offers.

Being a standard is BiDi's strength, and its age is its limit. Everything Strider does with Firefox goes through
commands any BiDi browser could implement, but the protocol doesn't yet cover all that CDP does: most of what
Firefox can't do in Strider, from media emulation to reading a paused response, is missing from BiDi or from
Firefox's implementation of it, and the [list below](#what-firefox-cant-do) says which.

Strider's tests run against Firefox 158.0. Other versions aren't tested.

## Launching

`Firefox.layer` launches the Firefox you name. Unlike Chromium's launcher, it connects to the browser over a
WebSocket, the only way Firefox's remote agent is reached, so it needs Effect's `WebSocketConstructor` as well as
the services every launch needs:

```ts
import { NodeServices, NodeSocket } from "@effect/platform-node"
import { Firefox } from "@usestrider/browser/firefox"
import { Config, Layer } from "effect"

const FirefoxLive = Firefox.layerConfig({
  executablePath: Config.String("FIREFOX_PATH")
}).pipe(Layer.provide([NodeServices.layer, NodeSocket.layerWebSocketConstructor]))
```

A launch runs Firefox with `--headless` (unless `headless: false`), `--remote-debugging-port=0`, `--no-remote` and
`--profile` pointing at a temporary profile, then your `args`. Strider reads the endpoint Firefox prints, connects,
and starts a session. A Firefox that reports no endpoint within 30 seconds fails the layer with `ConnectionFailed`,
or with `ProcessExited`, with the end of its output, if it exited.

The launch profile's preferences go into the profile's `user.js`. The default, `LaunchProfile.automation`, turns
off first-run pages, update checks and telemetry, and two things that change how pages behave:

- **The JSON viewer is off,** so a JSON response's document is the JSON as served, as it is in Chromium and WebKit,
  rather than Firefox's viewer.
- **Popups open as windows,** not tabs, for the reason in the next section.

`LaunchProfile.stock` sets nothing, and `LaunchProfile.concurrent` also turns off Firefox's throttling of background
timers. A profile's `args` are Chromium switches, which Firefox ignores. A `userDataDir` of your own is never
deleted, but Strider writes its `user.js` there too.

## Pages are windows

Firefox renders a tab that isn't in front about once a second. An action waits for the page to render before it
acts, so an action on a background tab would time out. So every page Strider opens is a window of its own, which
keeps rendering behind the others, and the default profile opens popups as windows too.

That covers what Strider opens. A tab of an [attached](#attaching) Firefox, or a popup under
`LaunchProfile.stock`, is still a tab: bring it forward with `yield* page.activate` before acting on it. Focus
emulation, `focus: "emulated"`, isn't available on Firefox.

## Attaching

Start Firefox with its remote agent, and `Firefox.layerConnect` attaches to it:

```sh
firefox --remote-debugging-port=9222
```

```ts
import { NodeSocket } from "@effect/platform-node"
import { Browser } from "@usestrider/browser"
import { Firefox } from "@usestrider/browser/firefox"
import { Effect, Layer } from "effect"

const Attached = Firefox.layerConnect("ws://127.0.0.1:9222").pipe(
  Layer.provide(NodeSocket.layerWebSocketConstructor)
)

const tabTitles = Effect.scoped(Effect.gen(function*() {
  const pages = yield* (yield* Browser.Browser).pages
  return yield* Effect.forEach(
    pages,
    (page) => Effect.flatMap(page.inspect, (tab) => tab.title)
  )
})).pipe(Effect.provide(Attached))
```

`/session` is added to an endpoint with no path. The tabs Firefox already has are observed: `inspect` or `control`
gains access to one for a scope, and they stay open when the program ends.

**Firefox allows one BiDi session at a time,** and a session outlives the connection that started it, until
something ends it. Strider ends its session when the layer's scope closes. While another client holds the
session, a connect fails with `ConnectionFailed`, whose hint says so. A program that dies before ending its session
leaves Firefox refusing every client until it restarts, unless the program was a `strider` session, whose
`strider prune --yes` stops the browser it launched.

An attached Firefox is the user's own, so Strider changes nothing about it: none of the profile's preferences
apply, its JSON viewer stays on, and its tabs are tabs. File choosers are left to the browser, because the setting
that answers them applies to the whole browser and would cancel the user's own. And a video can't be recorded,
because Firefox writes it on its own machine.

## What's different

**Init scripts run inside a function.** Firefox wraps each init script, so its top-level `var` and function
declarations aren't globals, as they are in Chromium and WebKit. Assign to `window` to share something between
scripts or with the page.

**Response bodies need a subscription first.** WebDriver BiDi keeps a body only when collection was set up before
the request started. In Strider that's what subscribing with `body` does anyway, as is `Har.record`; a response
that started before either has no body to give.

**An unhandled rejection looks like a throw.** Firefox reports a rejected promise nothing handled as an uncaught
exception, without saying which it was, so `UncaughtException`'s `kind` is `"unknown"` on Firefox.

**A cache and a service worker look alike.** Firefox marks responses from either as from the cache, so `servedBy`
is `"cacheOrServiceWorker"` for both. A script reused from the memory cache is reported as a request, where
Chromium and WebKit report nothing.

**Console text is Firefox's.** Firefox applies a call's format specifiers itself, and writes `%f` as printf does,
`1.250000`, where Chromium and WebKit, formatted by Strider, follow the Console Standard.

**Typing is key by key.** BiDi sends a key as its value, so a keyboard layout's AltGr and dead keys aren't sent
and the page sees a US key's `code`, and `insertText` types each character as a key.

**HTML drag and drop needs the page's help.** Firefox starts an HTML drag from input but never drops it. Use
`dragTo(target, { html: "synthetic" })`, which has the page dispatch the drag's events itself.

**Input into cross-site frames goes to the frame.** Firefox doesn't deliver input at page coordinates into a
cross-site iframe, so Strider sends it to the frame's own document instead. A drag from one document into another
goes to the first alone.

**Routes do less.** A request can't be sent on to a new URL, a response can't be fulfilled at the response phase
(changing its status and headers works), and every abort is the same failure, `"failed"`. An authentication
challenge nothing answers is canceled: Firefox's own answer is a prompt that waits forever when headless.

**Video, not frames.** Firefox records a page to a WebM file rather than streaming frames, so `Capability.Video`
works and `Capability.Screencast` doesn't. The file goes to the context's downloads directory, which a launched
Firefox has, and a trace's `screencast: "native"` uses it.

## Other WebDriver BiDi browsers

`Bidi.layerConnect` connects to any WebDriver BiDi endpoint, taken as given, with headers for the handshake, such as
a grid's token:

```ts
import { NodeSocket } from "@effect/platform-node"
import { Bidi } from "@usestrider/browser/bidi"
import { Config, Effect, Layer } from "effect"

const Grid = Layer.unwrap(Effect.gen(function*() {
  const token = yield* Config.Redacted("GRID_TOKEN")
  return Bidi.layerConnect("wss://grid.example.com/session", {
    headers: { authorization: token }
  })
})).pipe(Layer.provide(NodeSocket.layerWebSocketConstructor))
```

It's the same backend as Firefox's, so treat anything but Firefox as untested:

- **The capability list is Firefox's.** The backend reports what Firefox supports, whichever browser is at the
  other end.
- **It always starts a session.** An endpoint that hands out a WebSocket for a session it has already made may
  refuse that.
- **Files are on the other machine.** `FileInput.local` names a file on yours, which a remote browser can't read:
  use `FileInput.bytes`, or `FileInput.remote` for a file already on the browser's machine.

Safari Technology Preview implements only parts of BiDi so far, and reaching its BiDi endpoint takes a WebDriver
capability Strider doesn't set.

## The raw protocol

`@usestrider/browser/bidi-protocol` has every WebDriver BiDi command and event as a typed value, generated from the
specification, and `BidiConnection` runs them over a transport:

```ts
import { BrowsingContext, Session } from "@usestrider/browser/bidi-protocol"
import { BidiConnection, Protocol, Transport } from "@usestrider/browser/protocol"
import { Effect } from "effect"

const openTab = Effect.fn("openTab")(function*(endpoint: string, url: string) {
  const transport = yield* Transport.webSocket(endpoint)
  const bidi = yield* BidiConnection.make(transport)
  yield* Session.new_({ capabilities: {} }).pipe(Protocol.on(bidi.session))
  const { context } = yield* BrowsingContext.create({ type: "tab" }).pipe(
    Protocol.on(bidi.session)
  )
  yield* BrowsingContext.navigate({ context, url, wait: "complete" }).pipe(
    Protocol.on(bidi.session)
  )
})
```

It's the protocol and nothing more: no contexts tracked and no waiting for anything to be ready. Because Firefox
allows one session, a raw connection can't run beside Strider's own; and end your session with `Session.end` before
closing the socket, or Firefox stays locked. To see what Strider itself sends, turn on
`Browser.TraceProtocolCommands`, which adds a span for each command.

When Firefox rejects a command in an ordinary Strider call, the operation fails with `BackendFailure`, whose
`cause` is the `ProtocolError`, with Firefox's own error code and message.

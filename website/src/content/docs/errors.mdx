## Three kinds of failure

Every operation's error type says what it can fail with, and there are only three kinds:

| Error                      | Means                                                              | Carries                                    |
| -------------------------- | ------------------------------------------------------------------ | ------------------------------------------ |
| the module's own error     | the operation couldn't do what it was asked                        | a `reason`, a class with its own fields     |
| `TargetGone`               | something it needed ended: the page closed, the frame detached      | `reason`: why it ended                      |
| `Timeout`                  | the deadline passed                                                 | `phase`: how far it got                     |

Each module has one error: a click fails with `LocatorError`, a navigation with `PageError`, a download with
`DownloadError`, an expectation with `ExpectationFailed`. What went wrong is the error's `reason`, and every reason
has a `hint` that says what to do next. The message puts them together:

```
click page.getByRole("button", { name: "Save" }): 2 matches (2 elements match and 1 of them is visible; add .filter({ visible: true }))
```

Some reasons belong to one module, such as `Locator.StrictViolation` or `PageNavigation.NavigationFailed`. Others
are shared by every module, in `Reason`:

- `InvalidInput`: an argument the operation can't use, such as a selector that doesn't parse. It fails at once.
- `Unsupported`: this backend can't do it. The fix is a different browser, and the reason names the capability.
- `NotPermitted`: you don't hold the access this needs, such as acting on a page you may only inspect. The fix is
  a different call.
- `BackendFailure`: the browser refused or broke, with its own error attached.

## Recovering from what you expect

Errors are Effect errors, so everything Effect has for them applies. `Effect.catchReason` matches a module's error
and one of its reasons together, which is how you recover from a failure you expect without swallowing the others:

```ts
import { Locator, Page } from "@usestrider/browser"
import { Console, Effect } from "effect"

const listSuggestions = (violation: Locator.StrictViolation) =>
  Console.log("Several banners:", violation.suggestions)

const dismissBanner = Effect.fn("dismissBanner")(function*(page: Page.Page) {
  const accept = page.getByRole("button", { name: "Accept cookies" })
  yield* accept.click().pipe(
    Effect.catchReason("LocatorError", "StrictViolation", listSuggestions)
  )
})
```

A reason is the same class wherever it appears, so one check works across modules: `Effect.catchReason(tag,
"Unsupported", …)` for any module's tag.

## Strict by default

An action needs exactly one element. If the locator matches two, it fails at once with `StrictViolation`, listing
what it matched, and suggests `.filter({ visible: true })` when only one of them is visible. It doesn't wait to see
whether one goes away, because an ambiguous locator is a bug in the program, not a state of the page. Reads are
strict the same way.

If duplicates are expected to be brief, such as a toast fading out while the next one fades in, say so in the code
with an expectation before acting:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const dismissToast = Effect.fn("dismissToast")(function*(page: Page.Page) {
  const toasts = page.getByRole("status")
  yield* toasts.pipe(Expect.toHaveCount(1))
  yield* toasts.getByRole("button", { name: "Dismiss" }).click()
})
```

## Deadlines

Each operation has one deadline, which covers everything it does: waiting for its turn at the page's input,
finding the element, waiting for it to be ready, sending the input and confirming the result. With no deadline
around it, an operation gets the default budget, 30 seconds.

`Deadline.within` sets one deadline for everything inside it. The budget is shared, not per step: in this block,
the click, the navigation it causes and the expectation together have five seconds.

```ts
import { Deadline, Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const pay = Effect.fn("pay")(function*(page: Page.Page) {
  yield* page.getByRole("button", { name: "Pay" }).click()
  yield* page.getByText("Payment received").pipe(Expect.toBeVisible)
}, Deadline.within("5 seconds"))
```

A deadline inside another can only shorten it, never extend it. To change what operations get when nothing
encloses them, set the default budget for a program: `program.pipe(Deadline.withDefaultBudget("1 minute"))`.
`Deadline.remaining` reads the time left.

Deadlines run on a real clock, even inside a test that uses Effect's `TestClock`, so a test can move its own time
without making the browser's waits pass early or never.

## Timeouts say how far they got

A `Timeout` names its operation and its `phase`:

| Phase                   | The operation                                                                   |
| ----------------------- | ------------------------------------------------------------------------------- |
| `resolving`             | never found a matching element                                                   |
| `waitingForCondition`   | found it, but it never became ready: hidden, disabled, covered, moving           |
| `dispatchedUnconfirmed` | sent the input, and the page may have acted on it, but the result wasn't confirmed |
| `postcondition`         | acted, and what should follow never did, such as a navigation never committing    |

The phase matters most for deciding what to do next. Before `dispatchedUnconfirmed`, nothing reached the page,
and trying again is safe. After it, the click may have happened, so check the page's state before acting again:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const submitOnce = Effect.fn("submitOnce")(function*(page: Page.Page) {
  yield* page.getByRole("button", { name: "Submit" }).click().pipe(
    Effect.catchTag("Timeout", (timeout) =>
      Effect.gen(function*() {
        if (timeout.phase !== "dispatchedUnconfirmed") {
          return yield* Effect.fail(timeout)
        }
        yield* page.getByText("Submitted").pipe(Expect.toBeVisible)
      }))
  )
})
```

Strider never retries an action whose input may have reached the page. It does try again when it stopped a gesture
before the page's own handlers saw it, such as a click that would have landed on a toast.

## When expectations fail

`ExpectationFailed` says what was expected, what was seen last, and the history of what was seen, so a failure
answers "was it ever right?". When the locator found nothing, it also says what was nearest: what the page has
where the locator stopped matching, and locators for elements there whose names are close to the one asked for. A
typo in a button's name is usually obvious from the message alone.

## What a failure records

Every failure carries diagnostics: the operation's id and, for an action, its dispatch state, which answers "did my
click happen?":

- `NotSent`: nothing reached the browser.
- `MayHaveBeenSent`: the input was sent and its result is unknown.
- `Acknowledged`: the browser answered, `ok` or `rejected`.

Errors are Schemas, so they encode as data. The `strider` command and the agent toolkit return failures as data
too, hint and diagnostics included.

Diagnostics never show secrets. A value passed as `Redacted`, a cookie or a typed password is treated as secret,
and left out of messages, spans and logs. Under the default preset, `strict`, a URL keeps its origin and path with
each query value redacted; `Diagnostics.withPreset("local")` shows URLs whole while you're debugging.

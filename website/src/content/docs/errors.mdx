A failure that says only that something went wrong leaves you rerunning the program to find out why. Each of
Strider's says what happened, why and what to do, and is in the operation's type, so you can recover from the ones
you expect.

## Three kinds of failure

| Error                  | Means                                                         | Carries                                 |
| ---------------------- | ------------------------------------------------------------- | --------------------------------------- |
| the module's own error | the operation couldn't do what it was asked                    | a `reason`, a class with its own fields |
| [`TargetGone`](/docs/api/browser/Target#TargetGone) | something it needed ended: the page closed, the frame detached | `reason`: why it ended                  |
| `Timeout`              | the [deadline](/docs/deadlines) passed                         | `phase`: [how far it got](/docs/deadlines#timeouts) |

Each module has one error: `LocatorError` for a click, `PageError` for a navigation,
[`DownloadError`](/docs/api/browser/Download#DownloadError),
`ExpectationFailed`. Every reason has a `hint`, and the message includes it:

```
click page.getByRole("button", { name: "Save" }): 2 matches (2 elements match and 1 of them is visible; add .filter({ visible: true }))
```

Some reasons belong to one module, such as [`Locator.StrictViolation`](#strictness): the locator matched
more than one element. Others are shared, in `Reason`:

- `InvalidInput`: an argument the operation can't use, such as a malformed selector. Fails at once.
- `Unsupported`: this backend [can't do it](/docs/browsers/choosing#what-each-can-do). The reason names the
  capability.
- `NotPermitted`: you don't have the access it needs, such as acting on a page you may only inspect.
- `BackendFailure`: the browser refused or broke; its error is the `cause`.

## Recovering

Catch the reason you expect rather than the module's whole error, so every other failure still fails with its
message and hint. `Effect.catchReason` matches a module's error and one of its reasons. A step that needs a
capability some browsers lack can fall back when it's missing:

```ts
import { Page, Reason } from "@usestrider/browser"
import { Console, Effect, Option } from "effect"

const noPdf = (unsupported: Reason.Unsupported) =>
  Console.log(
    `No PDF: ${unsupported.capability} is unsupported on ${unsupported.backend}`
  ).pipe(
    Effect.as(Option.none())
  )

const invoicePdf = Effect.fn("invoicePdf")(function*(page: Page.Page) {
  return yield* page.pdf().pipe(
    Effect.map(Option.some),
    Effect.catchReason("PageError", "Unsupported", noPdf)
  )
})
```

A shared reason is the same class in every module, so one handler serves them all: `noPdf` would serve a
`LocatorError`'s `Unsupported` too.

## Strictness

Acting on the first of two matches would act on whichever the page rendered first, so a run could pass having
clicked the wrong button. An action or read needs exactly one element. Two or more fail at once with
`StrictViolation`, which lists them and suggests [`.filter({ visible: true })`](/docs/pages/locators#narrowing) when
only one is visible. Ambiguity doesn't wait: it's a bug in the locator.

When duplicates are brief, such as overlapping toasts, wait for them to settle first:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Effect } from "effect"

const dismissToast = Effect.fn("dismissToast")(function*(page: Page.Page) {
  const toasts = page.getByRole("status")
  yield* toasts.pipe(Expect.toHaveCount(1))
  yield* toasts.getByRole("button", { name: "Dismiss" }).click()
})
```

## Failed expectations

An expectation that runs out of time may have seen the wrong thing, or found nothing at all; `ExpectationFailed`
tells the two apart without a rerun. It has `condition` (what was expected), `last` (the last value seen) and
`history` (every value seen). When the locator matched nothing, `nearest` is an accessibility snapshot of what its
first steps found, up to the step that matched nothing, and `suggestions` are locators for elements with similar
names:

```ts
import { Expect, Page } from "@usestrider/browser"
import { Console, Effect, Option } from "effect"

const reportMissing = Effect.fn("reportMissing")(
  function*(failure: Expect.ExpectationFailed) {
    const last = Option.map(failure.last, (seen) => seen.value)
    yield* Console.error(`Expected ${failure.condition}, last saw`, last)
    yield* Console.error(Option.getOrElse(failure.nearest, () => "nothing near"))
    yield* Console.error("Did you mean:", failure.suggestions)
  }
)

const expectPlaced = Effect.fn("expectPlaced")(function*(page: Page.Page) {
  yield* page.getByText("Order placed").pipe(
    Expect.toBeVisible,
    Effect.tapErrorTag("ExpectationFailed", reportMissing)
  )
})
```

## Diagnostics

An action that fails may still have reached the page, so retrying it could submit twice. Every failure carries
`diagnostics`:

- `dispatch`, for an action: whether its input reached the page, `NotSent`, `MayHaveBeenSent` or `Acknowledged`.
- `progress`, for an [operation with steps](/docs/deadlines#operations-of-your-own): how far each step got.
- `operationId`: the id that links the failure to its operation's span and its entry in a
  [trace](/docs/tools/recordings#traces).

```ts
import { Page } from "@usestrider/browser"
import { Effect } from "effect"

const mayHavePaid = Effect.fn("mayHavePaid")(function*(page: Page.Page) {
  return yield* page.getByRole("button", { name: "Pay" }).click().pipe(
    Effect.as(true),
    Effect.catchTag(
      "LocatorError",
      (error) => Effect.succeed(error.diagnostics.dispatch._tag !== "NotSent")
    )
  )
})
```

Errors are Schemas, so they encode as data; the [`strider` CLI](/docs/agents/cli) and the
[agent toolkit](/docs/agents/toolkit) return them that way.

## Secrets and URLs

A failure's message ends up in logs, traces and bug reports, so `Redacted` values, cookies and typed passwords are
left out of it, and of spans and logs. A diagnostics preset sets how much of a URL they show: the default,
`strict`, keeps the origin and path and redacts query values, which can hold tokens. To see URLs whole while
debugging on your own machine, apply `Diagnostics.withPreset("local")` where a debug run starts, not inside a step:

```ts title="debug.ts"
import { NodeRuntime, NodeServices } from "@effect/platform-node"
import { Browser, Diagnostics } from "@usestrider/browser"
import { Chromium } from "@usestrider/browser/chromium"
import { Config, Effect, Layer } from "effect"

const openCart = Effect.scoped(Effect.gen(function*() {
  const page = yield* Browser.newPage()
  yield* page.goto("https://shop.example.com/cart?session=abc")
}))

const BrowserLive = Chromium.layerConfig({
  executablePath: Config.String("CHROMIUM_PATH")
}).pipe(Layer.provide(NodeServices.layer))

openCart.pipe(
  Diagnostics.withPreset("local"),
  Effect.provide(BrowserLive),
  NodeRuntime.runMain
)
```
